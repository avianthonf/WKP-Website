# Codebase Concerns

**Analysis Date:** 2026-04-22

## Tech Debt

**Duplicate Application Directory Structure:**
- Issue: The project contains both a root `/app` directory and a `/src/app` directory. The root `/app` directory contains the full implementation (5,900+ lines), while `/src/app` contains skeleton files with 1 line each. This creates extreme confusion and risk of editing the wrong files.
- Files: `app/`, `src/app/`
- Impact: Developers may inadvertently modify the skeleton files in `src/` expecting changes to take effect, or vice-versa. It also violates standard Next.js directory conventions where either root `/app` OR `/src/app` is used, but not both with identical structures.
- Fix approach: Delete the redundant skeleton files in `src/app` and consolidate everything into a single source of truth (likely root `/app` given its current state).

**Hardcoded Fallback Values in Env:**
- Issue: Sensitive or configuration-heavy values like the WhatsApp number have hardcoded fallbacks in the environment utility.
- Files: `app/lib/env.ts`
- Impact: If environment variables fail to load, the app reverts to a hardcoded WhatsApp number which might be incorrect for different environments or local testing.
- Fix approach: Use a strict validation library (like Zod) for environment variables and fail fast if required keys are missing, rather than providing "safe" but potentially incorrect defaults.

## Known Bugs

**Timezone Calculation Fragility:**
- Issue: The `store-hours.ts` logic uses `Intl.DateTimeFormat` parts to manually reconstruct local times and calculate offsets.
- Files: `app/lib/store-hours.ts`
- Symptoms: Potential for "off-by-one" hour errors during Daylight Saving Time (DST) transitions or in browsers with non-standard Intl implementations. The manual parsing of `shortOffset` (e.g., "GMT+5:30") is prone to error.
- Trigger: Cross-timezone orders or orders placed exactly during a DST shift.
- Workaround: Use a dedicated library like `date-fns-tz` or `luxon` for robust timezone handling.

## Security Considerations

**Supabase Service Role Key Usage:**
- Issue: The service role key is used in server actions and the storefront fetcher. While used server-side, it bypasses Row Level Security (RLS).
- Files: `app/actions.ts`, `app/lib/supabase.ts`, `app/lib/storefront.ts`
- Risk: If a server action is compromised or has a logic flaw (e.g., missing validation), the service role client allows full read/write access to the entire database.
- Current mitigation: Basic Zod validation in `actions.ts`.
- Recommendations: Implement strict RLS on all tables and prefer the `anon` key or authenticated user context where possible, reserving the service role only for truly administrative system tasks.

## Performance Bottlenecks

**Heavy Client-Side Bundle:**
- Issue: Core components like `cart-checkout.tsx` and `immersive-home.tsx` import large animation and icon libraries (`framer-motion`, `lucide-react`) and handle complex geolocation/state logic.
- Files: `app/components/cart-checkout.tsx`, `app/components/immersive-home.tsx`
- Problem: Large JS execution time on low-end mobile devices, which is the primary target for a pizza storefront.
- Cause: Excessive use of client-side logic for features that could be partially handled by Server Components.
- Improvement path: Audit `framer-motion` usage for simpler CSS transitions where possible and ensure icons are being tree-shaken correctly.

## Fragile Areas

**WhatsApp Message Construction:**
- Issue: The order handoff depends entirely on a URL string generated by `buildWhatsAppMessage`.
- Files: `app/lib/whatsapp.ts`, `app/actions.ts`
- Why fragile: If the message content exceeds URL length limits or contains characters that break the WhatsApp URI scheme, the customer cannot complete their order. There is no fallback if the browser blocks the `window.open` or redirect.
- Safe modification: Limit the amount of detail in the WhatsApp message to essential order info and provide a clear "Open WhatsApp" button as a fallback.

## Missing Critical Features

**Cart Persistence:**
- Issue: The cart appears to rely on a React Context (`cart-provider.tsx`) without explicit mention of `localStorage` or session persistence in the core logic.
- Files: `app/components/cart-provider.tsx`
- Problem: If a user refreshes the page or their mobile browser sleeps/reloads, their pizza customizations and cart items are lost.
- Blocks: High-conversion "return to cart" flows.

## Test Coverage Gaps

**Server Action Validation:**
- Issue: While `catalog.ts` has some tests, the critical `createWhatsAppOrder` action and its complex validation logic lack comprehensive unit tests for edge cases (e.g., invalid scheduled times, partial items).
- Files: `app/actions.ts`
- Risk: Changes to the order schema could break the ordering flow unnoticed until production.
- Priority: High
